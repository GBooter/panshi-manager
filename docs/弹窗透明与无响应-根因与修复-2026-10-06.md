# 弹窗「透明 + 无响应」根因与修复（2026-10-06）

> 用户报：系统保护页点「开启保护」按钮后，出现一个奇怪的透明弹窗——
> 能看到页面文字透出来，无法关闭、无法操作，且弹窗出现后软件其它位置
> 也都无法操作。
> 本文记录根因（两处叠加）与修复，并附带「开启保护」按钮语义优化。

---

## 一、结论速览

| 项 | 修复前 | 修复后 |
|---|---|---|
| 弹窗透明（看穿页面文字） | ❌ 页面文字直接透进弹窗 | ✅ 弹窗正常不透明（DTK 原生渲染） |
| 弹窗响应（悬停/点击/按键/Esc） | ❌ 完全无响应，Esc 也关不掉 | ✅ 全部正常 |

| 弹窗打开时主窗口可拖 | ✅（dragmodalprobe 6/6） | ✅ 保持 |
| 「开启保护（恢复只读）」按钮语义 | ❌ 保护已开启时仍显示可点按钮 | ✅ 保护已开启时显示「已生效」徽章 |

## 二、根因一：`disableDialogTransparency()` 关模糊导致弹窗看穿页面

### 2.1 症状与表象

弹窗中心区域能直接看到底层页面的文字（OCR 把页面文字与弹窗文字混读）。
像素级验证：页面文字像素（约 RGB 80）在弹窗打开后变为约 204 ——
即被弹窗半透明底色**透出**而不是**盖住**。

### 2.2 代码根因

`disableDialogTransparency()`（src/ui/components.cpp）用
`winId()` + `DPlatformHandle::setEnableBlurWindow(false)` 关掉 DTK 弹窗的
窗口模糊。但 **DDialog 自身背景是半透明的**（圆角 + 阴影设计，
开发指南 D2 同款教训）：模糊开启时毛玻璃兜底，视觉上"不透明"；
模糊一关，半透明底色直接透出底层内容，没有任何东西垫底。

曾尝试在函数里补 `setAutoFillBackground(true)` + 调色板强制 alpha=255，
**实测无效** —— DDialog 的背景由 DStyle/DPalette 专用绘制路径覆盖，
不读 QPalette::Window 的普通画刷。

### 2.3 修复

**不再跟 DTK 的弹窗渲染对抗**：`disableDialogTransparency()` 改为空操作，
保留 DTK 原生模糊渲染（即平台标准外观），签名保留仅为兼容 5 处调用点。
新增代码直接用 DDialog 默认渲染即可。

实测（X11 + kwin + dxcb）：保留模糊后弹窗背景不透明（≈RGB 234），
页面文字不再透出（透出点从 ≈204 恢复到 ≈235 = 被背景盖住）。

## 三、根因二：冻结内容区时把弹窗自己也禁用了

### 3.1 症状与表象

弹窗能画出内容，但**完全不响应任何输入**：
悬停无视觉反馈（像素 diff=0）、点击按钮无反应、Esc/Enter 无效。
WM 层 `_NET_WM_STATE_MODAL` 仍在（exec() 重设了模态）。

### 3.2 代码根因

`makeDialogNonBlockingWindowModal()`（src/ui/components.cpp）的「手动冻结」
方案：弹窗 Show 时 `centralWidget->setEnabled(false)` 冻结页面交互、
Hide 时恢复。但**弹窗以页面为父对象**（如 `ProtectionPage`），页面在
centralWidget 子树内 —— Qt 的禁用状态沿对象树传播，`dialog->isEnabled()`
按父链查询为 false，于是弹窗自身被禁用：悬停/点击/按键全部被忽略。

### 3.3 修复

冻结前先把弹窗**重挂到顶层窗口**（不在 centralWidget 子树内）：

```cpp
dialog->setParent(top);
if (!dialog->isWindow())
    dialog->setWindowFlag(Qt::Window, true);
```

冻结内容区不再波及弹窗本身；「用户不能越过弹窗操作页面」的语义仍由
内容区禁用保证。必须在安装冻结守卫**之前**重挂（守卫 Show 时才冻结，
弹窗 Show 后已随旧父链收到禁用，再搬来不及）。

### 3.4 验证

- 弹窗悬停 diff=19032（有反馈）、Esc 关闭、取消按钮关闭、单选可切换
- 内容区冻结：弹窗打开时点页面按钮无反应（仍同一个弹窗）
- dragmodalprobe 6/6 PASS（含「NonModal+冻结内容」场景）
- protectionprobe 44 项全 PASS

## 四、「保护开关」区域重设计（2026-10-06 第二轮）

### 4.1 用户反馈

上一轮把「开启保护（恢复只读）」行改成状态自适应（保护已开启时显示
「已生效」徽章）。用户重建后反馈：整个「保护开关」部分看着还是很怪。

### 4.2 问题分析

「保护开关」部分原先并存**三套功能重叠的控件**：

1. 「磐石功能」开关（总开关：开启/关闭，关闭时弹窗选临时/完全）；
2. 「开启保护（恢复只读）」行（保护未开启时恢复只读）—— 与开关「开」重复；
3. 「关闭保护（高级操作）」折叠区（永久/临时两枚按钮）—— 与开关「关」重复。

同一操作有三个入口、两套确认流程（页面内 setProtect 与
PanshiSwitch::requestSwitch），开关行 + 徽章行 + 折叠区层层叠叠，视觉上
自然"怪"。

### 4.3 修复：收敛为唯一入口

`PanshiSwitch::requestSwitch`（masterswitch.cpp）已能完整承担全部决策：

| 操作 | 交互 |
|---|---|
| 开启保护 | 拨开关 → 普通确认（"确定要恢复核心目录只读保护吗？此操作需要重启后生效。"） |
| 关闭保护（临时/完全） | 拨开关 → 单选弹窗（临时/完全 + 后果清单），完全关闭再走 30s 倒计时 |

故移除「开启保护」行与「关闭保护（高级操作）」折叠区，连同页面私有的
`setProtect()` 一并删除；「保护开关」部分只剩一行开关。跨页高亮
`highlightEnableProtect` 改为落在开关行上（备份页可写层冲突 → 跳本页 →
用户拨动开关即恢复只读）。「说明」区移到操作区之后作概念脚注，
并把「注意：开启可写层后系统将拒绝执行快照还原。」拆成警告色独立行。

### 4.4 页面最终结构

```
页头
┌ 只读保护 ┐ ┌ 可写层 ┐ ┌ 重启后状态 ┐        ← 3 卡时间轴
├──────────┤ ├────────┤ ├───────────┤
└──────────┘ └────────┘ └───────────┘
保护开关
┌────────────────────────────────────┐
│ 磐石功能         保护中·核心目录只读  [ON] │   ← 唯一控制入口
└────────────────────────────────────┘
说明（概念脚注：只读原理 + 可写层限制）
```

## 六、验证判据（防回归）

- **透字判据**：弹窗打开后，原先页面文字所在位置的像素应接近弹窗背景色
  （≈235），而非中间值（≈204 = 透出）。
- **响应判据**：鼠标悬停弹窗按钮区域应有像素变化（hover diff > 0）；
  Esc 与「取消」能关掉弹窗。
- **冻结判据**：弹窗打开时点页面控件无反应；弹窗关闭后页面恢复可点。
- 探针：`panshi-dragmodalprobe`（6 场景）、`panshi-protectionprobe`（44 项）。
