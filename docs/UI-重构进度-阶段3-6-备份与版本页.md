## 一、先说明：本轮有一处会**改变你上轮观测到的现象**

阶段 3-5 反馈里的第 2 条「20% 底色 —— 混合公式精确生效」采样到 `(204,204,204)`。

**本轮之后这个采样值会变**，原因不是"修好了"，而是这个现象本身改了实现路径：

| | 阶段 3-5（你采样的版本） | 阶段 3-6（本轮） |
|---|---|---|
| 策略提示条实现 | 自绘 `QFrame#panshiTipBar` + QSS `background: %ACCENTSOFT%` | `PanshiInlineBanner`（自绘圆角 + `Alpha::BannerFill`） |
| 底色表达式 | QSS 层用 `panshiSoftFill(Highlight)`（固定 alpha 38 ≈ 15%）再被 `%ACCENTSOFT%` 替换 | `softFill(semantic, 51)` 运行时混合 |
| 正文色 | `%ACCENT%`（主题强调色小字） | `Semantic::Normal`（中性正文）+ 语义图标 |

所以旧采样 `204 = 0.8×255 + 0.2×0` 对应的是**旧路径**：15% 的 `Highlight`，而 `TextLively` 在本环境为暗中性色 → 呈现灰。**新路径下采样点应按 `softFill(Warning|Accent, 51)` 重算**。

> ⚠️ 阶段 3-5 交接文档 §一 里"你上轮的修正被证实了"的结论**依然成立**——`softFill` 混合公式无误。这里只是提醒：拿旧采样值去比对新实现会得到"不一致"的误判。

### 3.2 表格列宽：`ResizeToContents` → `Interactive` + 弹性列

> ⚠️ **本节的列宽方案（7 列 / 描述列 Stretch）已被 §9.2 取代。** 保留原文以记录推导过程——
> 它错在"按最大化窗口做预算"，实测默认窗口态溢出 101px。**最终方案见 §9.2**：6 列、
> 名称与操作双弹性、固定列合计 443px。

**根因**：7 列中 6 列 `ResizeToContents`、只有描述列 `Stretch`。`ResizeToContents` 按**内容实际宽度**分配，宽窗口下"名称"列吃满、"操作"列被推出可视区；窄窗口下「系统初始备份」被压成 `Sy… ini…`。

新策略：

```cpp
for (int i = 0; i < 7; ++i)
    hh->setSectionResizeMode(i, QHeaderView::Interactive);
hh->setSectionResizeMode(4, QHeaderView::Stretch);   // 描述列吃掉剩余宽度
hh->setMinimumSectionSize(72);
hh->setStretchLastSection(false);                    // 关键：避免"操作"列被 lastSection 逻辑主导
```

初始宽度（`applyColumnWidths()`，只执行一次，之后尊重用户的拖动）：

| 列 | 0 名称 | 1 类型 | 2 时间 | 3 空间 | 4 描述 | 5 ID | 6 操作 |
|---|---|---|---|---|---|---|---|
| 宽度 | 200 | 110 | 150 | 110 | **Stretch** | 120 | 由布局决定 |

另加 `m_table->setWordWrap(false)`——单行内容不折行，行高恒 48。

> 说明：方案原文提过 `QTableWidget` → `DListView` + `DStyledItemDelegate`。本轮**没有**做这个迁移：表格的列对齐（时间/空间右对齐、类型居中）在手写 delegate 下要重实现一遍，收益主要是"更 DTK"，但风险是破坏用户已经验收过的排序/列宽手感。故保留表格，只清理它的 QSS（§六）。如果你希望按方案原文迁移，可以在 3-7 之后单开一轮，届时有 `m_table` 抽象封装会更容易替换。

### 3.5 还原流程：4 次打断 → 1~2 次

**旧流程**（最坏情况 4 次模态）：

```
点「还原」 → ① 还原对话框（DDialog 560，自绘 WarnBox + ⚠ 文字 + QGroupBox + 3 个 DRadioButton）
           → ② 二次确认（"请再次确认"）
           → ③ 还原就绪后：立即重启？（confirmDialog）
           → ④ 若不重启：infoDialog「请稍后手动重启」
```

**新流程**：

```
点「还原」 → ① 单次决策（PanshiUi::ConfirmRequest）：
                facts       = 目标备份 / 创建时间 / 描述
                consequences= 3 条后果（系统层修改丢失 / /home 不受影响 / 勿断电）
                options     = 3 个还原策略（单选，optionResult 回写）
                level       = Warning（确认按钮 Warning 色）
           → ② 还原就绪后：立即重启？（保留，这是"下一步动作"不是错误反馈）
                选「稍后手动重启」时改为 Banner Warning 常驻，不再弹 infoDialog
```

关键点：把原来的**自定义 DDialog 整块删掉**，改用 `PanshiUi::ConfirmRequest`——它在阶段 0 就已经支持 `facts` + `consequences` + `options/optionResult`，但此前**一直是零调用者**（你在阶段 1b 反馈里指出过这个"设计已完成、迁移未发生"）。本轮它终于被用上，还原对话框就是它的第一个真实用例。

旧实现里那个 `DFrame#panshiWarnBox` + `panshiWarnTitle` + `panshiWarnText` + `panshiDangerText` 全部随之下线。

## 四、DeploysPage 重写

结构与 SnapshotsPage 同构（Banner / L2 / EmptyState / Badge / 列宽），另有三处只属于本页的修正：

### 4.1 删除按钮：行下标 → commitId 复核（**真 bug**）

旧代码：

```cpp
connect(bDel, &DPushButton::clicked, this, [this, i] { onUndeploy(i); });
```

闭包捕获的是**行下标**。`refresh()` 后列表可能变短（例如刚删掉一个），此时旧闭包里的 `i` 指向的行已经不存在或已是**另一个部署** —— `onUndeploy(i)` 的边界检查（`index < m_deploys.size()`）挡不住"错位到邻居"的情况，会**删掉错误的部署**。

新代码：

```cpp
connect(bDel, &DPushButton::clicked, this, [this, i, commitId = d.commitId] {
    // 行下标在刷新后会错位，先按 commitId 复核，命中不了就放弃（宁可不删）
    if (i < 0 || i >= m_deploys.size() || m_deploys.at(i).commitId != commitId)
        return;
    onUndeploy(i);
});
```

复核不通过时**静默放弃**而不是删别的——删部署不可逆，"宁可不删"是对的默认。

### 4.2 「当前」徽章：`panshiTagPrimary` → `PanshiBadge(Accent)`

## 五、`BasePage::runAsyncQuiet()`（新增）

```cpp
/**
 * 静默执行：与 runAsync 相同，但完全不碰整页遮罩。
 *
 * 用于「切换标签页时的预读」——这类刷新紧跟在用户点击之后，此时再弹一次
 * 灰屏遮罩会在标签切换动画之上叠加一层闪烁，观感上像"闪两次灰屏"。
 */
```

**为什么需要它**：3-5 修掉了总览页的"连闪两次灰屏"（`m_maskEnabled` + 骨架屏分流）。但本页两个子页的路径不同——它们**切换标签时就会 `refresh()`**（`versionpage.cpp` 的 `currentChanged`）：

- 两个子页都已 `setMaskLoadingEnabled(false)`，所以 `runAsync` 不会盖遮罩；
- 但 `runAsync` 内部仍走 `if (m_maskEnabled) showLoading(...)` 这条分支——**行为上没问题，语义上悬着一根线**：将来有人把 `setMaskLoadingEnabled(false)` 去掉，遮罩立刻回来。

`runAsyncQuiet` 把"这类刷新本来就不该有整页遮罩"写成**代码事实**而不是"靠一个 flag 恰好关掉"，同时也给阶段 4 其它标签式页面（磁盘空间页有三个 tab）留了一个明确的工具。

回调里不再调 `hideLoading()`——静默执行没显示过遮罩，也就不该隐藏别人可能正在显示的遮罩。

## 九、编译侧反馈后的第二轮修正

### 9.1 编译错误（我的失误，你已修）

### 10.2 观察 ①「最窄态操作列 72px 装不下两个按钮」→ **采纳，但换实现**

用户原建议是对操作列单独放宽 `setMinimumSectionSize(120)`。**该 API 无法按列设置**：

- `QHeaderView::setMinimumSectionSize(int)` **只有全局版本**（`qheaderview.h#L126-129`，无按列重载）。
- 设为 120 会把 **6 列下限一起抬高** → 最小总宽 840px > 默认视口 761px → **重新出现横向滚动条**，退回刚落的问题。

**最终实现**：操作列改用 `QHeaderView::Fixed` + 常量 `kOperationColWidth = 170`：

```cpp
hh->setSectionResizeMode(0, QHeaderView::Stretch);   // 名称列吸收
hh->setSectionResizeMode(5, QHeaderView::Fixed);     // 操作列固定
hh->setMinimumSectionSize(72);
hh->setStretchLastSection(false);
m_table->setColumnWidth(5, kOperationColWidth);
```

- **为什么是 170 而非 120**：需容纳「还原」+「删除」两个按钮（各 4 个汉字，含内边距与 6px 间距），120 只够一个半按钮。
- **为什么操作列必须 Fixed、不能 Stretch**：`Stretch` 模式下列宽由 `QHeaderView` 每次布局重算，**`setColumnWidth` 对它无效**——空间不足时它一路缩到 `minimumSectionSize`（72px），外部无法校正。曾尝试挂 `geometriesChanged` 回调（`qheaderview.h#L160` 确有该信号）强制回写宽度，但无法稳定生效且有**递归风险**（`setColumnWidth` 本身会再次触发该信号），已放弃。
- **代价（已接受）**：横向空间不足时**只有名称列被压缩**（它有 `ElidedLabel` 兜底，是全表唯一适合被压缩的列）；名称压到下限后整表仍超宽才出现横向滚动条。固定列 443 + 名称下限 72 + 操作 170 = **685px < 761px**，默认窗口态不触发滚动条。

### 10.3 观察 ②「名称列初始 140px 即触发省略」→ **不采纳（不改）**

| 论据 | 说明 |
|---|---|
| 改动无效 | 名称列是 `Stretch`，布局每次都会按可用空间重算宽度，`setColumnWidth(0, 200)` 会被**立即覆盖**，对最终呈现零影响 |
| 改动有害 | 要让「First backup」完整显示约需 220px，而该宽度是从操作列（170px 固定）之外的可分配空间里抢的，会挤压其它列 |
| 现行为合理 | 初始 140px 触发省略是**默认窗口态下的信息密度取舍**；最大化后名称自动完整显示，且 tooltip 恒可兜底。1440p 及以上屏幕的默认窗口将不触发省略 |

| 实测阈值 | 视口 685px 对应窗口约 **984 逻辑宽**（1722 物理），比默认窗口窄约 8% 即触发 |

| 方案 | 评价 | 采纳 |
|---|---|---|
| 1. 接受现状 | 「删除」在极窄窗不可达 —— **信息丢失**，不是体验取舍 | ✗ |
| 2. 改 `makeScrollArea` 横向 `AsNeeded` | 全局 helper，会把**其它页**的意外超宽一并暴露；且整页（含页头/横幅/说明）出滚动条只为够一个按钮，UX 差 | ✗（原样） |

| **4. 表格自兜（本轮采用）** | 见下 | ✅ |

### 12.3 采用方案：让表格自己出横向滚动条

不改全局 `makeScrollArea`，改**表格自身**：

```cpp
// 1) 横向 SizePolicy 设为 Ignored —— 让布局彻底忽略表格的大小提示
//    （minimumSizeHint 里含 QHeaderView 按节累加出的宽度，是"钳住"表格的根因）
QSizePolicy sp = m_table->sizePolicy();
sp.setHorizontalPolicy(QSizePolicy::Ignored);
m_table->setSizePolicy(sp);
// 2) 显式小下限，避免被压到不可用
m_table->setMinimumWidth(320);
// 3) 横向溢出交给表格内部滚动条
m_table->setHorizontalScrollBarPolicy(Qt::ScrollBarAsNeeded);
```

- **为什么是对的**：表格能真正缩进视口 → 外层不再有可裁之物；列宽合计（685）大于表格宽度时，滚动条出现在**表格内部**，页面整体布局（页头、横幅、说明、下方备注）不受影响。
- **与「接受截字」的本质区别**：截字是**信息丢失**，滚动条是**信息可达**——后者才是闭环。
- **为什么不是方案 2**：全局改会同时暴露其它页可能存在的意外超宽（症状外溢），且整页横向滚动条的语义不清；把问题收敛在表格内部，作用域最小、语义最清晰。
- **默认窗口态不受影响**：表格是布局中的 stretch 项，`Ignored` 只影响 sizeHint、不影响填充行为，默认窗口下仍占满可用宽度（761px > 685px，无滚动条）。

**同步应用到 `DeploysPage`**：同因同治（其固定列合计 587px，同一阈值机制）。
