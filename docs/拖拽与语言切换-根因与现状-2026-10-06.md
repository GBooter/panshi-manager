## 二、拖拽 ↔ 点击：二选一的互斥关系（本轮最重要的发现）

### 2.1 为什么会有互斥

本工程编译时 **`DTK_TITLE_DRAG_WINDOW` 宏未定义**（sysroot 与 build flags 全搜不到），
而 `dtitlebar.h` 把拖动信号包在 `#ifdef DTK_TITLE_DRAG_WINDOW` 里：

```cpp
#ifdef DTK_TITLE_DRAG_WINDOW
    void mousePosPressed(Qt::MouseButtons buttons, QPoint pos);
    void mousePosMoving(Qt::MouseButton button, QPoint pos);
#endif
```

⇒ **DTitlebar 自带的拖动状态机根本没编进来**。
X11 下窗口移动只剩 dxcb 插件的 `DNoTitlebarWindowHelper`
（`DVtableHook` 钩 `QWindow::event` → 发 `_NET_WM_MOVERESIZE_MOVE`），
而该钩子**只对被 `setEnabledNoTitlebarForWindow(win, true)` 标记为无标题栏的窗口安装**。

### 2.2 A/B 双向实测（同一坐标、同一二进制，只切这一个开关）

| `kEnableCSD` | 拖拽 | 侧栏点击切页 |
|---|---|---|
| `true` | ✅ 窗口 798,130 → 858,190，3/3 成功 | ❌ **diff = 0 像素**，标题栏 ☰ 菜单也点不开 |
| `false` | ❌ 完全不动 | ✅ **diff = 33,281,800 像素**（画面全变），QListView 收到 11 次 PRESS |

事件过滤器证据：CSD 开启时 `QListView` / 标题栏按钮**确实收到了 `MouseButtonPress` 与
`MouseButtonRelease`**（坐标正确，如 `(76,143)`），但**不产生任何动作**
⇒ 钩子在 `QWindow` 层吞掉了点击语义，不是「事件没送到」。

### 2.3 当前取舍

**默认 `kEnableCSD = false`**（`src/mainwindow.cpp`）：**点击可用 > 拖拽可用**。
理由：点不动 = 整个应用不可用；拖不动还有 `Alt+F7` / 窗口菜单 / Super+拖 等替代。

要恢复拖拽：把 `kEnableCSD` 改 `true`，但**必须同时接受整窗点不动**。

### 2.4 ⚠️ 本轮踩过的假阴性（务必记住）

- 判「点击失效」时一度用 `import -window` 截图对比，得到 `diff = 0` 就下了
  「点不动」的结论 —— **错**。截图是缩放过的（1080px 宽代表 1854px 设备像素，
  比例 1.717），我按截图坐标点击，**点到了「总览」这一页自己**（本来就选中）
  ⇒ 必然 0 变化。**改用按比例换算后的坐标，diff 立刻变成 33M。**
- 另一处假阴性：点在了**分组标题行**（`beginGroup` 加的行带 `Qt::NoItemFlags`，
  不可点），坐标看起来「在侧栏里」，但不是可点项。
- 教训（与 MEMORY 中「探针 PASS 要抽验它真能 FAIL」同源）：
  **判据必须先证明「在有效输入点上确实会产生可见变化」**，否则 0 变化有两种
  截然不同的含义（真失效 / 点错地方），不可混为一谈。

## 三、语言切换：为什么之前「没效果」

### 3.1 三轮实证（推翻直觉）

| 做法 | 结果 |
|---|---|
| `QLocale::setDefault(en_US)` | ❌ 完全无效 |
| 进程**启动前**设 `LANGUAGE=en_US` | ✅ 有效 |
| 在 `main()` 内部 `qputenv("LANGUAGE","en_US")` | ❌ 无效 |

**根因**：DTK 的 `loadTranslator()` 走 **`QLocale::system()`**，
而它是**进程启动时由 C 库缓存**的 locale —— 运行期改环境变量**太晚**，改不动它。
诊断证据：env 里 `LANGUAGE=en_US`、`QLocale().name()=en_US` 全都对，
但 `QLocale::system()` 仍是 `zh_CN`，译文依旧中文。

### 3.2 最终方案（`src/main.cpp`）

1. 读 `QSettings("deepin","panshi-manager")` 的 `language`；
2. 显式 `setlocale(LC_ALL, "en_US.UTF-8")` 同步 C 库 locale；
3. `app.loadTranslator()` **之后**，自行 `QTranslator::load()` 对应 `.qm` 并
   `installTranslator()` —— **后装载的优先**，覆盖 DTK 装的那份。
   搜索顺序：`~/.local/share/panshi-manager/translations` → `/usr/share/...`
   → 可执行文件同级 `translations/` → 可执行文件同级。
4. 重启自身时用 `qputenv` 把 `LANGUAGE`/`LANG` 传给子进程，
   并**清掉 `LC_ALL`**（它优先级最高，残留会覆盖选择）。
   ⚠️ `LANG` 必须写成带 codeset 的合法 locale（`en_US.UTF-8`），裸 `en_US` 会挑不到 `.qm`。

### 3.3 实测结果

| `language` | 窗口标题 | 判定 |
|---|---|---|
| `en_US` | `Panshi Manager` | ✅ |
| `zh_CN` | `磐石设置` | ✅ |
| `system` | `磐石设置` | ✅ |

新增的 4 个菜单串（`语言` / `跟随系统` / `简体中文` / `English`）已 `lupdate` 提取并
补齐 en_US 译文（en_US 现有 **520 finished / 0 unfinished**）。

## 四、桌面环境里的一个干扰项（非本应用问题）

X stacking 实证：有一个外来窗口 `0x1c067e2`（1923×1225，`+639+341`，
无 `WM_NAME` / `_NET_WM_PID` / `_NET_WM_WINDOW_TYPE`，Override Redirect = no）
**盖在本应用之上**。关键判据：**不启动本应用时它也一直存在**
⇒ 与本代码无关，是环境里的常驻窗口（录屏/截图/远控类工具常见）。
它会影响自动化点击测试的准确性（`xdotool` 点击可能被它吃掉），
排查时先用 `xwininfo -root -children` 确认堆叠顺序。

## 五、HighDpi 警告

用户报告每次启动都出现：

```
setHighDpiScaleFactorRoundingPolicy must be called before creating the QGuiApplication instance
```

本轮**在本机复现不到**（`grep -c` 于运行日志 = 0 次），且该警告**不影响功能**。
代码里该调用已放在 `main()` 最前面、任何 `QGuiApplication` 之前，顺序正确。
⇒ 暂按**环境差异**处理（用户 shell 与本工具进程的启动环境不同）。
若你那边仍在出现，可执行 `strace -e trace=execve ./build/panshi-manager 2>&1 | head`
确认是否有包装脚本/别名先启动了 GUI 程序。

## 六、本机复现 GUI 的坑（每次都会踩）

- `XDG_RUNTIME_DIR` 必须指向**真实存在**的目录，否则
  `QLocalServer::listen：未知错误 22` → 应用秒退（**别当成崩溃**）。
  本工具进程以 root 运行 ⇒ 需 `/run/user/0`（已创建）。
- **Bash 工具每次调用是独立沙箱、进程不跨调用保留** ⇒ 启动与检测必须放同一次调用；
  且上一轮残留的实例会让下一轮 `xdotool search --pid` 抓到**旧窗口**，
  造成「刚改好的代码测出来still失败」的假象 —— 每轮前先 `pkill -9 -f panshi-manager`。
- 判「dxcb 是否生效」只能看 `/proc/<pid>/maps`，`platformName()` 不可信。
- 找窗口要用 `--pid` + `_NET_WM_WINDOW_TYPE` 过滤；`xdotool search --name "磐石设置"`
  会误匹配文件管理器。注意 dxcb 会把窗口拆成多个原生子窗口，**面积最大的那个才是主窗口**。
- 窗口坐标：`import -window` 截图为缩放图（1080px ↔ 1854px，比例 1.717），
  **截图坐标必须按比例换算成设备像素再拿去点击**。
