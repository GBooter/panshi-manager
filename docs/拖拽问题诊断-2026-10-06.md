# 窗口拖不动 —— 根因诊断与修复（2026-10-06）

> 结论先行：**无条件状态下窗口拖拽一直是好的**。用户看到的「拖不动」有明确触发条件 ——
> **模态对话框打开期间**。前三轮怀疑的 CSD / dxcb 钩子 / 高 DPI 警告，全部被实测推翻。

## 一、被推翻的假设（勿重复走）

| 假设 | 实测结果 | 判据 |
|---|---|---|
| `setHighDpiScaleFactorRoundingPolicy` 警告导致拖不动 | **无关**。该警告在所有成功拖动的运行里都出现 | 5 轮连测，拖动 5/5 成功 |
| CSD（`setEnabledNoTitlebarForWindow`）没开导致拖不动 | **无关**。`if (false && ...)` 禁用后仍可拖 | 反向验证 |
| dxcb 插件没生效 | **无关**。`/proc/<pid>/maps` 确认 `libdxcb.so` 已加载 | 实际加载的库 |
| 窗口被 `WM_HINTS` 标记为不可移动 | **无关**。`WM_HINTS` 无 modal 标记 | `xprop` |
| 665x210 的隐藏 DIALOG 窗口挡住主窗口 | **无关**。它是 dxcb 的 titlebar 子窗口（`Map State: IsUnMapped` 属正常）；`xunmap` 前后拖拽行为无差异 | `xwininfo` + A/B |

> ⚠️ `platformName()` 返回 `"xcb"` **不能**用来判断 dxcb 是否生效 ——
> `libdxcb.so` 同时以 `xcb`/`dxcb` 两个 key 注册，Qt 取第一个匹配。

## 二、真正的触发条件

`QDialog::exec()` 默认 `Qt::ApplicationModal`，会建立**模态 grab**。
`DTitlebar` 是主窗口的子控件，grab 期间它收不到 `MouseButtonPress`，
拖动状态机无从启动 ⇒ 窗口拖不动。

与用户描述完全吻合：按钮点击"仍然有效"（点的是对话框上的按钮，不是主窗口），
且「能点、能最大化最小化」也不矛盾（那些由 WM 处理，不经 Qt 事件分发）。

## 三、弯路：WindowModal 也不管用

第一版修复把 `ApplicationModal` 降为 `WindowModal`，看着像"降级"。
探针一跑就露馅：

```
SCENARIO WindowModal 打开中 | MODAL=1 | 主窗口可拖=否 | 期望阻塞=否 | FAIL
```

`DDialog` 的 modality 确实变成了 `WindowModal`，但 `activeModalWidget()` 仍非空 ——
**WindowModal 的 grab 范围恰好覆盖父窗口**，而标题栏正是父窗口的子控件。

⇒ 任何形式的"模态"都不解决问题。必须让主窗口**根本不是模态目标**。

## 四、最终方案：非模态 + 手动冻结内容区

`PanshiUi::makeDialogNonBlockingWindowModal()`（`src/ui/components.cpp`）：

1. 对话框设为 `Qt::NonModal`（不建立任何 grab）
2. `centralWidget()->setEnabled(false)` —— 页面内按钮/开关全部点不动
3. **不 disable 主窗口本身** ⇒ 标题栏保持可用，窗口随时可拖
4. 对话框关闭（`QHide`）或析构时自动恢复内容区

确认框的语义保住了（用户不能越过对话框去操作页面），且窗口不再"卡住"。

### 实现要点（三个坑）

- **恢复钩子用 `QEvent::Hide` 事件过滤，不用 `QDialog::finished`** ——
  `DDialog`/`PanshiCountdownDialog` 继承的是 `DAbstractDialog`（`QWidget`），
  **没有 `finished` 信号**，用它会直接编译失败。
- 过滤器必须 `setParent(dialog)` 随 dialog 析构，否则 `installEventFilter`
  不接管寿命 → 泄漏且回调打到已死对象。
- `content` 用 `QPointer` 保护：dialog 析构时 content 可能先没（父子顺序不保证）。
- 无 parent、或父窗口取不到 `centralWidget()` 时**不做任何改动** ——
  认不出来就不动，避免"看起来改了其实没改"的静默失效。

## 五、探针 `panshi-dragmodalprobe`

6 个场景，覆盖"能拖"与"不能拖"两种结果（**判据有效性自检**）：

| 场景 | 期望 | 结果 |
|---|---|---|
| 无对话框 | 可拖 | PASS |
| ApplicationModal 打开中（修复前行为） | 阻塞 | PASS |
| 对话框关闭后 | 可拖 | PASS |
| NonModal + 冻结内容（修复目标） | 可拖 | PASS |
| 内容区应被冻结 | 是 | PASS |
| 无 parent 对话框不改动 | 保持原样 | PASS |

### ⚠️ 判据有效性已验证（防假阴性）

单点回退 `content->setEnabled(false)` → 重编 → `内容区应被冻结 FAIL`，
`SUMMARY PASS=5 FAIL=1`。**探针确实能测到该缺陷**，恢复后 6/6 PASS。

> 📌 这条验证是必须的：双向都 PASS（假阴性）比 FAIL 更危险 ——
> 它会让你以为"探针失效/修复无效"，实际是判据测不到该缺陷。
> 本项目已因此白查过一轮（见 MEMORY.md 第四节第 3 条）。

## 九、追加：改为「窗口管理器交互式移动」并查证「拖出屏幕边缘」（2026-10-06 下午）

### 9.1 本次修改（mainwindow.cpp）

旧的「X11 手动 setPosition 跟随」已移除，标题栏左键按下即
`windowHandle()->startSystemMove()`（X11 发 `_NET_WM_MOVERESIZE_MOVE`，
Wayland 走合成器 move）。理由与实测：

- **旧方案**：`setPosition()` 是客户端 configure 请求，KWin 对其执行
  `keepInArea(geometry, workArea)` —— **整窗钳制在屏内**（实测 xdotool
  windowmove -600 → 停在 0；2900 → 1346，恰好右缘贴边）。
- **新方案**：WM 原生交互式移动，拖动平滑、点击不互斥（与之前一致的
  DTitlebar::mousePressed 路径），且拖到屏幕边缘会触发 KWin 的**边缘分屏**
  （拖到左缘松开 = 平铺到左半屏），体验更佳。

### 9.2 「窗口能否部分拖出屏幕边缘」—— 结论：不能，且是 WM 全局行为

用户希望「一部分窗口放到桌面边缘之外」。实测（kwin_x11 6.1.38，Debian 维护
的上游 KWin，**非 Deepin 分支**）：

- 交互式移动中窗口 x 到达 0 即被钳制（拖 -600/-900 均停在 x=0，宽度不变）；
- 松开时若在左缘，KWin 执行边缘平铺（窗口变 1600=3200/2 宽）。
- KWin 源码（Plasma/6.1）的交互式移动约束是「标题栏保持可见」，
  本应允许部分出屏；但**实测本机被钳在整窗可见**（可能发行版合入补丁，
  或 CSD 无 WM 边框时 titleBarRect 高度为 0 触发另一分支）。
- `adjustWindowPosition` 的边缘吸附（BorderSnapZone 默认 1px）不解释 x=0 的
  硬钳制。

⇒ **任何应用都无法通过 setPosition / startSystemMove 把窗口拖出屏幕边缘**，
这是 KWin 对所有窗口的全局行为，磐石设置只能保证「拖动正常 + 边缘平铺可用」。

### 9.3 验证要点（避免误判）

- 用 `xdotool search --pid <PID>` 按尺寸筛主窗口（1854x1225 物理 =
  1060x700 逻辑 × 1.75 DPI），**勿用 --name**（会命中 deepin-terminal 的
  「磐石设置 - 终端」窗口）。
- 合成拖拽用**慢速分步**（每步 -250px + sleep）才可靠；`startSystemMove`
  触发后 KWin 接管，快速一次性 mousemove 可能不被处理。
- xdotool 的 keydown Shift 在本机**不生效**（KWin 读不到修饰键），
  无法用 Shift 验证「禁用边缘平铺后能否出屏」。
- 拖拽后窗口若变 1600x1908@(0,0)，是「边缘平铺」而非 bug；恢复用
  `xdotool windowsize 1854 1225 && windowmove 566 539`（平铺态需先解除）。

### 9.4 补充实测（2026-10-06 晚）：右缘可出屏、左缘被钳制 —— 精确行为与结论修正

§9.2 的旧结论「任何方向都不能出屏」**不完整**。当日稍晚在**同一环境**
（kwin_x11 6.1.38 + dde-kwin 6.0.9，X11，屏幕 3200x2000，窗口 1854x1225 物理）复测：

| 动作 | 实测结果 | 结论 |
|---|---|---|
| 交互式移动拖到**右缘外**（指针 1051→2460，窗口 x 551→2731） | 窗口右缘 = 4585 > 3200，**确实拖出右缘** | 右缘允许出屏 |
| 交互式移动拖到**左缘外**（指针 500→-300，逐点记录） | 窗口 x 跟随指针直到 x=0，**此后钳在 0**（指针继续为负窗口不动） | 左缘硬钳制在 x≥0 |
| 松开在左缘 | KWin 执行**边缘平铺**（窗口变 3200/2 宽 @(0,0)） | 平铺正常 |
| 客户端 `setPosition` / xdotool windowmove -600 | x=0；windowmove 3500 | 右缘 = 3200 贴边 | 整窗 keepInArea，**双侧**都钳在屏内 |

⇒ 精确结论：**dde-kwin 的交互式移动约束是「窗口左上角不越过工作区左上角」
（x≥0, y≥0 的单侧最小约束）**，因此：
- 右缘 / 下缘：可以拖出屏（无上限约束）；
- 左缘 / 上缘：被钳在 0，任何应用都无法通过 startSystemMove 拖出；
- 客户端 setPosition 更差：keepInArea 把**整窗**钳在屏内（双侧都不行）。

这是 WM 对所有窗口的**全局行为**，磐石设置（及任何普通应用）在应用层无法绕过：
两条可用机制（startSystemMove / setPosition）都被 WM 约束。若要让左缘像右缘一样
可拖出屏，改动必须落在 **dde-kwin 窗口管理器**（放宽交互式移动的最小位置约束），
不属于本应用范畴。本应用维持 §9.1 的 startSystemMove 方案（拖动正常 + 右/下缘
出屏 + 边缘平铺），这已是应用侧的最优解。
